# API reference

Base path `/api`. JSON in, JSON out. Interactive docs (Swagger) at `/docs` while the app runs.
Real request/response examples for every case are in [`api-examples/`](api-examples/) — generated by the actual backend
(`python backend/scripts/generate_api_examples.py`), each file as `{"_http_status": …, "body": …}`.

**Conventions** — money is a whole-rupee integer (INR). Dates `YYYY-MM-DD`; date-times `YYYY-MM-DDTHH:MM`, always **local time of the place**
(no UTC offsets). Child = age 0–17. IDs are strings (`pkg_…`, catalog ids).

## Build — `POST /api/packages`

Request (exactly the 7 form fields; `traveler_name` is optional and not part of the UI):
```json
{ "departure_city": "Bengaluru", "country": "Japan", "start_date": "2027-04-10", "nights": 6,
  "adults": 2, "child_ages": [6], "budget_inr": 350000 }
```

Always HTTP 200 for these three outcomes (`outcome` tells which); only invalid input is 422.

| `outcome` | When | Key fields |
|---|---|---|
| `PACKAGE` | A valid package fits the budget | `package` |
| `OVER_BUDGET` | Valid packages exist but none fits | `cheapest_total_inr`, `over_by_inr`, `message`, `alternatives[]` (each a saved draft package: `label`, `levers`, `changes`, `total_inr`, `remaining_inr`, `package_id`), `raise_budget{budget_inr, extra_needed_inr, label}` |
| `NO_PACKAGE` | Nothing is possible | `reason_code`, `message` |

`reason_code` values: `OUT_OF_WINDOW`, `NO_ARRIVAL_FLIGHT`, `INSUFFICIENT_SEATS_ARRIVAL`, `NO_RETURN_FLIGHT`, `INSUFFICIENT_SEATS_RETURN`,
`NO_CITY_PLAN_FOR_FLIGHTS`, `NO_ROOMS`, `NO_AIRPORT_TRANSFER`, `NO_CITY_TRANSFER`, `NOT_ENOUGH_ATTRACTIONS`.

**Raising the budget:** call `POST /api/packages` again with `budget_inr` set to `raise_budget.budget_inr`.
**Opening an alternative:** `GET /api/packages/{alternative.package_id}`.

Invalid input → **422**: `{"error": {"code": "VALIDATION_ERROR", "message", "fields": [{"field", "message"}]}}` — one entry per bad field.

## The package object

Top level: `package_id`, `status`, `variant`, `request`, `traveler`, `country`, `start_date`, `end_date`, `city_plan[]`, `pricing`, `metrics`,
`items[]`, `days[]`, `warnings[]`, `reservation`. See [`api-examples/build_package_menon.json`](api-examples/build_package_menon.json).

**Item** — shared trip format (`item_id`, `type`, `name`, `city`, `status`, `catalog_id`, `start`, `end`, `room_id`, `quantity`, `price_inr`,
`booking`, `sources`, `warnings`) plus UI helpers:

| UI field | Use |
|---|---|
| `title`, `subtitle` | Plain-language text to show |
| `icon` | `flight`, `hotel`, `taxi`, `bus`, `train`, `attraction` |
| `badges[]` | `DIRECT`, `ONE_STOP`, `FAMILY_FRIENDLY`, `FREE`, `CHILD_FRIENDLY` |
| `image` | Path under `/images/…` (or `null`) |
| `leg` | `ARRIVAL`/`RETURN` (flights), `AIRPORT_ARRIVAL`/`AIRPORT_DEPARTURE`/`INTERCITY` (transfers), `STAY`, `VISIT` |
| `day` | Date the item belongs to |
| `pinned` | `true` if the traveler chose it (never dropped silently) |

**Day** — `{date, weekday, city, kind, summary, events[]}`; `kind` is `ARRIVAL`, `FULL`, `CITY_CHANGE` or `LAST`; each event is
`{item_id, time, time_label, type, icon, label}` already sorted by time.

## Changes — `POST /api/packages/{id}/changes`

| `op` | Fields |
|---|---|
| `CHANGE_HOTEL` | `city`, `hotel_id`, `room_id` |
| `CHANGE_FLIGHT` | `leg` (`ARRIVAL`/`RETURN`), `flight_id` |
| `ADD_ATTRACTION` | `attraction_id`, `date`, optional `start` (`HH:MM`; omitted = earliest free slot) |
| `REMOVE_ATTRACTION` | `item_id` |
| `CHANGE_CITY_PLAN` | `plan`: `[{"city": "Tokyo", "nights": 3}, {"city": "Kyoto", "nights": 3}]` — the nights must add up to the trip length |

Optional on any op: `raise_budget: true` (accept going over budget — the budget becomes the new total) and
`remove_pinned_conflicts: true` (accept dropping a traveler-chosen visit that no longer fits).

| `result` | Meaning | Fields |
|---|---|---|
| `APPLIED` | Saved | `package`, `price_delta_inr`, `summary`, `changed_item_ids`, `warnings` |
| `REFUSED` | A hard rule would break; nothing changed | `reason_code`, `reason`, `suggestion?`, `violations?` |
| `BUDGET_EXCEEDED` | Legal but over budget; nothing changed | `new_total_inr`, `over_by_inr`, `message`, `suggestion`, `raise_budget_to_inr`, `cheaper_options?` |
| `PINNED_CONFLICT` | Something the traveler chose can't be kept | `reason`, `suggestion`, `options[]` |

`reason_code` values: `PACKAGE_LOCKED`, `UNKNOWN_OP`, `INVALID_CITY`, `HOTEL_NOT_FOUND`, `ROOM_NOT_FOUND`, `ROOM_DOES_NOT_FIT`,
`ROOMS_UNAVAILABLE`, `NO_AIRPORT_TRANSFER`, `INVALID_LEG`, `FLIGHT_NOT_FOUND`, `FLIGHT_MISMATCH`, `AIRPORT_MISMATCH`, `SEATS_UNAVAILABLE`,
`ATTRACTION_NOT_FOUND`, `INVALID_DAY`, `INVALID_TIME`, `ATTRACTION_WRONG_CITY`, `ATTRACTION_CLOSED`, `ATTRACTION_DUPLICATE`,
`ATTRACTION_OUTSIDE_HOURS`, `ATTRACTION_OVERLAP`, `ITEM_NOT_FOUND`, `INVALID_PLAN`, `VALIDATION_FAILED`.

## Options

Every option has `available`, `fits_budget`, `budget_needed_inr`, `price_delta_inr` (change in the **whole package total**, including knock-on
transfer changes) and `current` (the choice already in the package). Unavailable options are still listed with `reason_unavailable` and
`reason_code` so the UI can grey them out with the reason. Hotel options also carry `name`, `stars`, `rating`, `area`, `room_name`,
`rooms_needed`, `family_friendly`, `image`; flight options carry `airline`, `flight_number`, `departure`, `arrival`, `stops`,
`duration_minutes`, `seats_left`; attraction options carry `start_choices[]` (valid `HH:MM` start times).

## Confirm and reservations

`POST /api/packages/{id}/confirm` → `{"reservation_number": "9872917955", "package": {…status "BOOKED"…}}`. Repeating the call returns the
same number. A package that no longer passes every rule gets `409 PACKAGE_INVALID`; if another booking has taken the last seats or rooms it gets `409 INVENTORY_CONFLICT` with a plain message (nothing is booked). Booked packages are locked (`PACKAGE_LOCKED`).
`GET /api/reservations/{number}` → the booked package, or `404 RESERVATION_NOT_FOUND` for any number that doesn't exist or isn't 10 digits.

## Export

`GET /api/packages/{id}/export` returns the shared trip format: `trip_id`, `traveler`, `start_date`, `end_date`, `country`, `budget_inr`,
`total_inr`, `status`, `items[]`. Hotel items have `room_id`; flights carry the **arrival city**; after confirm every item is `BOOKED` with
`booking.reference` set to the reservation number as a string.

## Error shape (everything else)

`{"error": {"code": "…", "message": "…"}}` — `PACKAGE_NOT_FOUND` / `RESERVATION_NOT_FOUND` / `NOT_FOUND` (404), `METHOD_NOT_ALLOWED` (405),
`PACKAGE_INVALID` / `INVENTORY_CONFLICT` (409), `INTERNAL_ERROR` (500, no stack trace).

## Extra features

### Package variants — `POST /api/packages/variants`
Same request body as build. Returns `{"outcome": "VARIANTS", "recommended": {…}, "variants": {"cheapest", "best_rated"}, "notes": []}`;
every package is complete, valid, within budget, saved with its own `package_id`, and carries `variant` (`CHEAPEST`, `BEST_RATED`,
`RECOMMENDED`). The traveler picks one and continues with its id. Over-budget and impossible requests return the same `OVER_BUDGET` / `NO_PACKAGE`
bodies as build. *Cheapest* = lowest total; *best rated* = highest average hotel stars per
night within budget (guest rating ignored). Ties are broken by the lower price. See `variants.json`.

### Change cities — `GET …/options/city-plans`, then `CHANGE_CITY_PLAN`
Each option: `plan[]`, `cities`, `city_count`, `total_inr`, `price_delta_inr`, `fits_budget`, `budget_needed_inr`, `transit_minutes`,
`avg_hotel_stars`, `preferred` (the app's preferred city count for this many nights), `current`, `warnings[]` (e.g. `RUSHED_PLAN`).
Applying a plan rebuilds the whole package but **keeps what the traveler chose** (hotels, flights, attractions) wherever it is still valid; anything
that cannot carry over returns `PINNED_CONFLICT` with `options` (`KEEP_CURRENT` or `APPLY_AND_REMOVE`, which is re-sent with
`remove_pinned_conflicts: true`). A plan over budget returns `BUDGET_EXCEEDED` unless re-sent with `raise_budget: true`.
Examples: `options_city_plans.json`, `change_city_plan_applied.json`, `change_city_plan_pinned_conflict.json`, `change_city_plan_refused_invalid.json`.

### Quick request — `POST /api/parse-request`
Body `{"text": "Japan 10 Apr 6 nights 2 adults 1 child 6 from Bengaluru 3.5 lakh, we like history and nature"}` → `{fields, understood[], missing[], unparsed[], notes[], ready}`.
Interest words (history, culture, nature, parks, theme parks, art, food, markets, views, adventure …) fill `fields.interests` in the order typed; a bare "family" is not an interest.
`fields` uses the same names as the build request, so a `ready: true` result can be posted as-is. Anything not understood is listed in `missing`;
guesses are explained in `notes` (e.g. "No year given, so 2027 was assumed", "Read “kids 1” as one child aged 1 — please check the age");
a note containing "please check" makes `ready` false. Understands dates (`10 Apr`, `April 10 2027`, `10/04/2027`, `2027-04-10`, ranges like `10 Apr to 16 Apr`),
nights (`6 nights`, `6n`, `7 days` = 6 nights), budgets (`3.5 lakh`, `350k`, `₹3,50,000`), adults (`2 adults`, `couple`, `solo`), children and ages,
and city aliases (Bangalore, Bombay, Madras, Dubai, UAE…). Examples: `parse_request.json`, `parse_request_needs_check.json`.

### Booking uses up seats and rooms
`POST …/confirm` checks the package's seats and room-nights against the catalog **minus our own confirmed bookings** and records the usage in the same
transaction. If the last seats or rooms are gone it returns `409 INVENTORY_CONFLICT` (message names the flight or hotel) and books nothing; the traveler
can rebuild. Builds, options and changes always use these reduced numbers. The data files themselves are never modified. See `confirm_inventory_conflict.json`.

### Undo — `POST /api/packages/{id}/undo`
Restores the previous version of a package (up to 20 steps; history survives restarts). Returns `{"result": "UNDONE", "package", "summary", "undo_available"}`,
or `REFUSED` with `NOTHING_TO_UNDO` / `PACKAGE_LOCKED` (booked packages cannot change). Every `APPLIED` change response includes `undo_available: true`.

### "Why this plan" and "knock-on" notes
Every package has a `rationale`: `{headline, reasons[], alternatives_hint}` — plain sentences built from the real itinerary (why this many cities, travel time,
flights and arrival, hotel quality, budget used, sights, and what the traveler chose themselves). Every `APPLIED` change also returns `knock_on[]`:
sentences about *other* bookings that moved because of it (e.g. "Your airport pickup on arrival moves from 10:20 am to 11:30 am").

> **Fetch options again after every change.** Hotel, flight and city-plan options describe the package as it is *now*; a change (or a raised budget) can alter them.


### Interest tags — optional `interests` on every build
`GET /api/meta` returns `interests: [{id, label}]` (`HISTORY_CULTURE`, `NATURE`, `FAMILY`, `ART`, `FOOD_MARKETS`, `VIEWS_ADVENTURE`).
Send `"interests": ["ART", "NATURE"]` (ids or labels, any case; duplicates dropped; unknown tag → 422 on field `interests`) with the 7 fields, on `POST /api/packages` or `/variants`.
The engine uses fixed keyword rules on `attractions.json` (category, name, aliases; no AI) to prefer matching sights **after** child suitability and **before** variety and price; opening hours, overlaps and the budget are never relaxed.
In the package: `request.interests`; on each sight `badges` gets `MATCHES_INTEREST` and `details.interestTags` / `details.matchedInterests`.
`GET …/options/attractions` adds `matches_interests` / `matched_interests` to each option and lists matching ones first. Interests survive changes, undo, city-plan changes and variants; they are not part of the exported trip JSON.

### Pocket city guide and nearby dining
Both come from separate static files in `backend/app/content/` (never `data/catalog/`, never in the export, never in the price).
`/api/cities/{city}/guide` → `{city, country, tagline, getting_around[], etiquette[], sightseeing_tips[], good_to_know[], source}`.
`/api/packages/{id}/dining` → `{stays: [{item_id, hotel, city, area, restaurants: [{name, cuisine, dietary_tags[], estimated_price_per_person_inr, price_label, note}]}], disclaimer, included_in_total: false}`.
Show `price_label` ("≈ ₹… per person (estimate)") and the disclaimer next to the list. Unknown city → 404 `CITY_NOT_FOUND`.

### Route map — `package.route`
Every package (and so every variant and every changed package) carries `route`: `{origin: {city, airport, lat, lng}, stops: [{order, city, nights, check_in, check_out, hotel, lat, lng}],
legs: [{order, kind: FLIGHT|INTERCITY, direction, mode: FLIGHT|TRAIN|BUS|TAXI, from, to, label, duration_minutes, duration_label, …}], path: [city…], summary: {cities, nights, travel_minutes, travel_label, label}}`.
Draw departure hub → stops (in `order`) → back, with each leg's mode and duration; re-render whenever you receive a new package.

### Why this plan — extra sentences
`rationale.reasons` now also states the airport safety margins actually achieved (pickup ≥ 60 min after landing, airport ≥ 180 min before the flight home), the rooms chosen for the party size, and how many sights match the traveler's interests.
